## 1. Design language for this surface

### 1.1 Feeling, in Iris's order (value and chroma before hue)

Built to read as *unhurried, warm, quietly joyful — a little world apart* (Nadia §5.1; evidence grade **moderate** — strong cross-cultural association literature for light values + gentle saturation reading as positive and low-arousal; induced-feeling effects are weak and are not claimed). The house knowingly trades the peak pleasantness of loud, saturated palettes for quiet wonder; that trade is stated here because a reviewer will ask. This is a working team's gallery, not a landing page: nothing in the visual language persuades, converts, or performs for search. It orients, it hangs pictures well, and it gets out of the way.

### 1.2 Value key and grounds

Light key, exactly as `theme.park` assigns it. Four grounds do all the work, plus one dark ground (§2) used in exactly three places:

| Role (token) | Value | Where it lives in the museum |
|---|---|---|
| `sys.color.bg` = `paper-1` | #F7F1DE | Page ground, everywhere by default |
| `sys.color.surface` = `paper-0` | #FFFDF4 | Cards, fields, panels, the art-stage mat |
| `sys.color.bg-recessed` = `paper-2` | #F1E8CF | Recessed wells only (skeleton beds, the Dahlias letter-group wells if needed). **No gold-ink text ever sits here** (Ada ruling 1, in the token file) — and no link text of any kind is set on paper-2 in this design |
| `sys.color.text-strong` = `deep` | #23362B | Header/footer ground (existing `SiteHeader`/`SiteFooter` dress), selected chip/segment fills, primary buttons |
| `sys.color.ground-evening` *(new, §8)* = `deep-2` | #1C2A21 | The museum's one dark ground: piece-view photo stage, the player, the Listening Room head, the track-view head. Nothing else |

Text steps on the light grounds are the token set's own: `ink` #2E4438 body (9.30:1 on paper-1, *token*), `pine-2` #43534A muted (7.22:1, *token*), `sage-ink` #4E5D47 faint (6.24:1, *token* — the only text-weight sage). Headings are `deep`. Links and quiet-button text are `gold-ink` #86691F (4.59:1 on paper-1, 5.08:1 on paper-0, *token*) — used at `label` size and up, never for long body text, per its token description.

### 1.3 Chroma budget and gold discipline

Neutrals + gold own the space at roughly 60-30-10 (Nadia §5.1). Bloom accents appear **only** as wing-marker fills (§1.4) and inside the artwork itself — never as text, never as a selected state, never as the only carrier of a distinction. Selected states everywhere use the component tokens that already exist: `comp.chip.selected-bg` / `comp.segmented.selected-bg` = `deep` fill with `paper-1` text (11.38:1, *computed*), so selection reads identically in every wing regardless of that wing's accent.

Gold, restated because a museum reaches for it constantly: `gold-2` #B08D37 is graphics/rules/stitch only, never text (2.77:1 on paper-1, *token*); `gold-3` #927128 is large text, graphics, and the light-ground focus ring (4.03:1 on paper-1 — graphics/large only, *token*); `gold-ink` is the only text gold; on dark grounds `gold-1` #E8CF8F is the accent text (9.81:1 on deep-2, *computed*). The card stitch (`comp.card.stitch`, 1.5px dashed gold-3 at 45%) is the museum's one decorative signature, used on the About card, the art-stage mat, and wing entry cards — nowhere else, so it stays a signature instead of becoming wallpaper.

### 1.4 Wing markers — colour + shape + label + position

Each wing gets a marker built from four redundant channels, so wing identity survives protanopia, deuteranopia, tritanopia, and full grayscale:

1. **Shape** — a distinct silhouette per wing (below).
2. **Accent fill** — one bloom accent per wing, used as *infill only*.
3. **Label** — the wing's name in `ink` text beside the marker, always. The marker never appears as the sole identifier in navigation, cards, or piece views.
4. **Position** — the job-ranked order (Dahlias, The Park, Listening Room, Art & Motifs, Arcade) is identical in the header nav, the phone strip, the entrance directory, and every "next wing" exit. Position never changes.

The marker's **boundary** is what carries its shape against the ground, so every marker is drawn with a 1.5px ring in `deep` on light grounds (11.38:1 against paper-1, *computed* — the shape is identifiable even if the fill is not) and a 1.5px ring in `paper-1` on the evening ground (13.26:1 against deep-2, *computed*). The fill is therefore free to be any bloom accent, including the two that cannot themselves reach 3:1 against paper — they are decoration inside a boundary that already passes, and the label beside them does the identifying. This construction is listed for Ada's confirmation at §7 (flag AF-3).

| Wing | Shape | Fill (token) | Fill vs paper-1 | Fill vs paper-0 | Notes |
|---|---|---|---|---|---|
| Dahlias | Disc (circle, `radius.full`) | `dahlia-coral` #D1603D | 3.41 *(computed)* | 3.78 | The bloom itself; also passes 3:1 as a graphic in its own right |
| The Park | Arch (flat base, full-radius top) | `sky` #5B6FA6 | 4.35 | 4.83 | Open sky over the grounds; the darkest fill |
| Listening Room | Pill (horizontal bar, `radius.full`) | `marigold` #E9B83A | 1.63 | 1.81 | Lightest fill; a sound-bar silhouette. Fails 3:1 on paper by itself — carried by ring + label + position, per the construction above |
| Art & Motifs | Square (`radius.sm` 8px) | `lavender` #8E6CC0 | 3.68 | 4.08 | Pigment/craft register |
| Arcade | Rounded square (`radius.lg` 16px) | `dahlia-pink` #D77FA8 | 2.48 | 2.75 | Play register; fails 3:1 on paper by itself — same carrying construction as marigold |

By relative luminance the fills order marigold (lightest) → dahlia-pink → dahlia-coral → lavender → sky (darkest): five distinct value steps as well as five hues, so even in grayscale the markers separate — with one honest caveat: coral and lavender are the closest value pair, and they are separated by shape (disc vs square) and by distance in the fixed order (positions 1 and 4). `dusty-rose` #C98BA6 is **deliberately not used** as a marker: it sits too close to dahlia-pink in both hue family and value, and a sixth near-duplicate would weaken the set. It remains available to Elena inside artwork, where it already lives.

Marker sizes: 20px in the phone wing strip and nav-adjacent contexts, 24px in entrance wing cards and wing heads, 16px in cross-wing chips (highlights, search results, piece-view eyebrow). The marker is a presentational element (`aria-hidden`); the adjacent text label is the accessible name.

### 1.5 Shape, elevation, spacing, icons — the system, not invention

- **Radius language** (from `ref.radius`): cards `lg` 16px to `xl` 24px (the `comp.card.radius-min/max` band); fields `md` 12px; the player 22px (`comp.player.radius` — a component value, referenced, not re-derived); buttons and chips `full`; the evening panels `xl` 24px; the photo stage `xl` on desktop, square (full-bleed) on phone.
- **Elevation ladder** (from `sys.elevation`): `flat` for gallery grid cells (a wall, not a stack of cards); `card` for entry cards, panels, and the art mat; `header` for the sticky controls row when stuck; `player` for the docked player (its shadow colour is already deep-2-based, which is one reason §2.2's evening player sits naturally in the system); `sheet`/`dialog` are not used — the museum has no sheets or dialogs.
- **Spacing**: component steps from `ref.space` (2/4/8/12/16/20/24/32/40/48px as `.025`–`.600`), section steps from `ref.layout` (16/24/32/48/64/96px as `.200`–`.1200`). Page gutter: `layout.200` (16px) on phone, `layout.400` (32px) on desktop, inside a 1280px content cap (`comp.header.bar-max-width`). Density is the system's *comfortable* visitor density (`comp.density.comfortable-*`): card insets 20px phone / 24px desktop, row height 48px. This is a browsing surface for the team, not an admin tool — no compact density anywhere.
- **Icons**: the existing `@hues/ui` `Icon` component and its set only — 24px grid, 20px live area, 1.8 stroke (`comp.icon.*`). Icons used: `search`, `play`, `pause`, `next` (and its mirrored pair for Previous, as the set's chevron pair is used by `BackPill`), `chevron-left/right`, `close` (chip removal), `share`, `external` (arcade out-links, View full size), `info`/`warning`/`error` (state regions, via the components that already own them). No new icon family, no wing glyphs — the `Icon` set has none, and §1.4's shape markers do that job instead. Icons never carry a critical action alone; every icon control in this design has a visible or accessible label, per Nadia §3.

## 2. The two flagged items — decided

### 2.1 The piece-view viewing ground: `deep-2`, for photographs only

**Decision: the viewing ground is `deep-2` #1C2A21, taken into the park theme as one new system token, `sys.color.ground-evening` (§8). No new colour is invented** — the value is the existing reference colour, given a role name so no screen hard-codes it.

Why deep-2 and not the other candidates:

- **`frame` #16241B — rejected.** Its token job is the dashboard frame and dark-theme ground. The museum borrowing it would import the dashboard's association into a gallery and spend a token outside its role — exactly the "choose tokens by meaning, not by the colour that happens to match" failure my playbook warns against.
- **`deep` #23362B — rejected, narrowly.** It is already the header/footer ground and the selected-fill colour. A stage in `deep` would make the piece view read as an extension of the chrome rather than a room of its own, and would blur the selected-state fill's meaning (a photograph's surround should never look like a giant selected chip).
- **`deep-2` — chosen.** Its recorded roles are "deepest ground; evening surface," and a viewing stage *is* an evening surface: a darkened room for looking. Its measured pairs are the strongest of the three for everything that must sit on or against it (table at §7): paper-1 text 13.26:1, gold-1 accent text 9.81:1, sage-1 secondary text 10.15:1, gold-2 graphics/focus ring 4.79:1, poppy player dot 3.73:1 — all *computed* this pass. It also unifies the museum's dark moments: stage, player, and Listening Room head share one ground and read as one register (§2.2).

**Scope of the ground — a stage, not a page.** The evening ground is a panel the photograph sits *in*, with `space.200` (16px) of surround on phone and `space.400` (32px) on desktop. The piece's title, captions, details, and actions stay **below the stage on paper-1**, exactly as Nadia §4.1/§5.3 require — no text is overlaid on the photograph, and the only text that ever appears on the stage itself is the broken-image state's message and its gold-1 "Open the original file" link (13.26:1 and 9.81:1 respectively). The image link's focus treatment on this ground is the token system's deep-ground pair: `gold-2` ring with `paper-1` offset (`focus-ring-deep` / `focus-offset-deep`).

**The paintings rule — my position, and what still needs a word.** Iris's playbook states the house rule without exceptions: *dahlia paintings are never placed on dark green grounds.* I am not asking for an exception, and this design does not take one:

- The evening stage is specified **for photographs only** — cultivar photos and park photographs. A photograph's dark surround is a mat/frame convention: the picture's own colours were fixed by the camera, and a quiet dark mat is the standard gallery treatment that lets them read at full value (simultaneous contrast working *for* the piece).
- **Every painted piece** — Art & Motifs exhibits, painted plates, any painted park artwork — is shown on the **art stage**: a `paper-0` panel at `elevation.card` with the `comp.card.stitch` border inside it and a `space.300` (24px) paper mat between panel edge and artwork, `fit=pad` onto the paper ground (the `Image` component's plate treatment, `comp.image.plate-pad`). Paintings never touch the evening ground in any wing, on any screen, including highlights and search results. The piece-view template therefore has two stage variants, chosen by the catalog's media kind, not by taste per piece.
- **Still flagged for Iris + Elena (flag FE-1):** confirm that *photographs* on deep-2 does not collide with the spirit of the rule. My reasoning is above (the rule names paintings; its evident purpose is protecting watercolour luminosity, and a painting's ground becomes part of the artwork in a way a photograph's mat does not). But the rule is theirs to interpret, and if they rule that the spirit covers photographs too, the fallback is already designed: every stage becomes the art stage (paper-0 mat), and nothing else in this document changes. The build should not start the stage component until their word lands.

### 2.2 The Listening Room evening treatment: player + room head + track head — not the whole room

**Decision: the evening register covers exactly three surfaces** — (1) the docked player, on every screen where it appears; (2) the Listening Room's room-head panel on `/music`; (3) the track view's head panel on `/music/:slug`. **The track list, the desktop context column, and every other part of `/music` stay on paper.**

Why not the whole room:

- The museum's value key is light (§1.2). A full-screen dark room would break the one-register-per-visit rhythm and make the Listening Room feel like a different product bolted onto the museum — the "five products" failure, in one wing.
- Nadia's simultaneous-contrast argument only needs a *threshold*: one dark panel at the top of the room makes the paper-bright galleries — and the list directly below it — read brighter, and matches how the music is actually met at the park (evening, string lights) without darkening the working surface the team scans to find a track.
- The track list is a scanning surface. `TrackRow`'s dress, its playing-state wash (`comp.card.wash`), and the poppy dot are all specified and measured on paper grounds; moving 38 rows onto deep-2 would require re-dressing and re-measuring every row state to solve a problem the head panel already solves.
- The player is a listening *object*, not a page region: it travels across wings while music plays, and its evening dress is what marks it as the park after dark, wherever it docks. Its shadow token (`sys.elevation.player`) is already deep-2-based, so the evening player is the system's own intention, surfaced.

All text and graphics on the evening surfaces use only the pairs measured at §7: `paper-1` for titles and body, `sage-1` for secondary/meta text, `gold-1` for eyebrows, links, and the progress elapsed fill, `gold-2` for rings, the progress track, and focus, `poppy` for the play fill and dot (graphics only, glyph/label always alongside), `white` for the play glyph on poppy (4.01:1 — a graphic, held to the 3:1 non-text floor, §7 flag AF-1).

**Card-crop anchoring — `cropFocus` (gate F7).** Nadia's catalog (§4.3 of the UX doc) carries an optional per-piece `cropFocus` — a CSS position pair (e.g. `50% 30%`), set by the catalog pass from Elena's art-direction crop directions; centre when unset. This paragraph is the component anchor that field's spec points to; the `card` slot consumes it as follows:

- Every cover crop rendered from slot `card` sets the image's `object-position` to the piece's `cropFocus`. That is the whole mechanism: the box ratio never changes, the delivered asset is the width-ladder rendition of the whole frame (no server-side ratio crop that could discard the focal region before the browser sees it), and the browser's cover crop pivots on the focal point instead of the centre.
- **Slots that honour it:** the `ExhibitCard` photo treatment (both ratios — the Q2 portrait variant included), `CultivarCard`, and the `ContentCard` media slot on the entrance wing cards — in short, every grid, band, highlights, search, and entrance cover crop.
- **Slots that ignore it:** the piece-view stage (slot `hero` — whole frame, nothing is cropped, §4.8), every `plate` treatment (fit pad, never cropped — a focal point has nothing to act on), and all non-image components.
- **Default and failure:** field absent → `object-position: 50% 50%` (centre), which reproduces the pre-F7 behaviour exactly. A malformed value is the catalog pass's validation problem; the component passes the value through unparsed and falls back to centre rather than rendering an unanchored crop. The field never alters alt text, layout, or the reserved ratio box, so the CLS discipline (§4.2) is untouched.

**Portrait card variant (gate Q2 — Elena's instruction answered).** Elena's art direction for Visitors at Dusk (`hues/park/visitors-evening-dahlia-beds.jpeg` — highlights slot 3 and the Park wing's photographic lead) instructs: portrait ratio, *do not force it into a landscape crop*, focus on the table and buckets. A fixed 4/3 cover box cannot honour that — it would amputate exactly the portrait composition she is protecting. **The reconciliation is a variant, not an exception:** `ExhibitCard`'s photo treatment chooses its box from the catalog's native aspect for the piece — landscape or square pieces render at 4/3 as specced above; **a portrait piece (native height greater than width) renders at ratio 3/4**, fit cover, with `cropFocus` anchoring what little crop remains when a native ratio is taller than 3/4 (for Visitors at Dusk: the table and buckets, per Elena). The rule is aspect-driven and general — any portrait photograph in any wing takes the variant automatically from its catalog dimensions; there is no per-piece hand-flag for a builder to forget. Grid behaviour: the cell keeps its column width and its title stack follows its own image; a row containing a portrait cell grows to that cell's height and landscape neighbours top-align — accepted in the Highlights and Park grids, the places portrait photographs actually occur, and visible nowhere else. The piece view is untouched (whole frame on the stage, as always). Elena's instruction is answered by construction, not overridden: no portrait photograph in this museum is ever forced into a landscape crop.

**Explicitly not used, with reasons:** `Pagination` (Nadia forbids numbered pagination — Show more is a `Button`), `TabBar` (no tab bar in this IA), `AdminShell`, `Sheet`, `Dialog`, `FormDialog`, `SignupCard`, `DataTable`, `UpdateNotice`, `OfflineBanner` (no PWA, no forms beyond search, no admin, no overlays in Nadia's flows — inventing a use for any of them would be structure work, which is not mine).

### 3.4 Icon style statement

One family (the shipped set), one stroke language (1.8 on the 24 grid), sizes from `comp.icon.size-*` (16/20/24px) chosen by optical size for context — 20px inside 44px controls, 16px inline beside `label`/`caption` text, 24px for the player's transport glyphs inside their 44px rounds. ## 6. Motion

Tokens only (`ref.motion`): `press` 150ms, `state` 200ms, `sheet` 300ms, `reveal` 700ms, `highlight` 1200ms, one easing `ease.out` cubic-bezier(0.22, 0.9, 0.3, 1). There is no other easing and no other duration in this design.

| Moment | Treatment |
|---|---|
| Tap/press on any control | Selected state renders in the **same frame** (Nadia's ≤0.1s acknowledgement; no transition on the state itself — `press` 150ms applies only to the button's existing scale feedback) |
| Chip / toggle / letter selection | Fill and label swap at `state` 200ms, `ease.out`; the control does not resize, move, or remount |
| Show more append | New cells fade in at `reveal` 700ms as one group (not staggered — a wall being hung, not a performance); no scroll movement |
| Entrance first paint | Highlights and wing cards settle at `reveal` 700ms, once, on first load only; never on return navigation |
| Player dock/undock | `sheet` 300ms slide + fade (§5) |
| Skeleton breathe | `highlight` 1200ms, the shipped `Skeleton` behaviour |
| Route changes | No page transition. The SPA swaps content in place under a persistent shell (Nadia's model); inventing a crossfade would fight the return-to-place behaviour |
| Letter jump / group jump | `scroll-behavior: smooth` at the platform's own timing — the one place motion explains where something went |
| **`prefers-reduced-motion`** | All of the above become instant: no fade, no slide, no breathe (skeleton renders static), letter jumps become immediate (`scroll-behavior: auto`). Playback progress is always paired with its text readout, so no information rides on motion (Nadia §5.3) |

No auto-advancing anything, no parallax, no hover zooms on photographs (a museum does not lean toward you), no animated markers.

### 7.2 Targets, focus, and state channels

- **Targets:** every interactive element ≥ 44px (`comp.shell.target-min`): chips, letter buttons (44×44 exactly), player controls (44px rounds), field height 48px, prev/next 56px, big play 64px. Grid images on phone at 2 columns in a 320px viewport are ≥136px wide — never a target-size problem.
- **Focus:** 2px ring + 2px offset everywhere (`comp.shell.focus-*`), ground-following: on light grounds `gold-3` ring with `deep` offset; on evening grounds `gold-2` ring with `paper-1` offset. Sticky stacks and the docked player carry scroll-margins so focus is never obscured (§4.0, §5).
- **State never by colour alone:** current wing = label weight + underline + `aria-current` (marker is the fourth channel, not the first); selected letter/chip/segment = fill + text contrast change + persistent applied chips; playing track = dot + semibold title + text label + `data-state` on the row — never `aria-current`, which is the wing nav's alone (F18 record, §3.1); voice = a printed word on every row.
- **Resize/reflow:** layouts are specified at 320px with no two-dimensional scrolling (the letter bar and wing strip wrap; nothing scrolls sideways); text is set in the token roles with no fixed-height text containers, so 200% resize and the 1.4.12 spacing overrides reflow instead of clipping — the build must verify this at Quinn's gate on the live surface, at real sizes, per my playbook; this document specifies, it does not claim a render check it has not performed.

- **AF-2 — phone navigation at 320px.** My solution is a wrapping strip that takes three rows at 320–359px and is non-sticky (§4.0, FLAG-N1). No semantics change is proposed (it remains a labelled nav list with `aria-current`), so this may need no ruling — but Nadia §5.3 flagged the nav question for Ada if the strip couldn't hold, and at 320px it holds only by wrapping further; her confirmation that the three-row wrap satisfies the floor is asked, alongside Nadia/Hue's sign-off on the deviation.

## 8. Build-ready token / CSS checklist

### 8.1 The one new token

Exactly one token is proposed, through the design-system process (DTCG file `theme.park.json`, tokens package, with its contrast pairs added to that package's pair tests):

```json
"ground-evening": {
  "$value": "{ref.color.deep-2}",
  "$type": "color",
  "$description": "The museum's dark ground: piece-view photo stage, docked player, Listening Room and track-view heads. Value is the existing evening reference colour; this token names the role so no surface hard-codes deep-2. Text pairs on it: paper-1 13.26:1, gold-1 9.81:1, sage-1 10.15:1 (computed 2026-11-25, Mina)."
}
```
as `sys.color.ground-evening` in the park theme. **No new reference colour, no new hex, no other new token.** The `MuseumPlayer` evening variant and the `ContentCard` media slot (§3.2) are component work in `@hues/ui`, consuming existing tokens; `WingMarker`, `ExhibitCard`, `LetterBar`, and `EveningHead` (§3.3) are new components built entirely from existing `sys`/`comp` tokens plus this one.

### 8.2 Tailwind mapping notes (where Tailwind is used)

Latest Tailwind, values mapped onto the @hues tokens via `@theme inline` — tokens own every value; Tailwind is only the utility vocabulary:

- Colours: `--color-*` from `sys.color.*` (bg, surface, bg-recessed, text, text-strong, text-muted, text-faint, accent-ink, ground-evening, and the five `ref.color` bloom accents exposed **only** as marker-fill utilities, named by wing — `--color-marker-dahlias` etc. — so no utility exists that could set them as text colour by accident beyond what CSS allows; the naming is the guardrail).
- Spacing: the `ref.space` / `ref.layout` scales as the spacing theme; no arbitrary spacing values.
- Type: `sys.type` roles as composite text utilities (family + weight + size + leading + tracking travel together, per Thea's composite-token rule) — a builder must never assemble a role from raw size utilities.
- Radius, elevation, motion: `ref.radius`, `sys.elevation`, `ref.motion` (duration + the single easing) mapped as theme values.
- The museum ships **no dark-mode variant**: its grounds are token roles chosen per component (paper vs evening), not a `prefers-color-scheme` theme. A system dark-mode flip must not invert the museum — the evening panels are dark in a light museum by design, in both system modes.

### 8.3 What must NOT be hard-coded (build review checklist)

- No hex anywhere in app code — every colour is a `sys`/`comp` token (the five marker fills included, via §8.2's wing-named utilities).
- No raw px for spacing, radius, or type — token names only; the exceptions that already exist as component-contract values (player radius 22px, control sizes) are referenced from `comp.*`, not re-typed.
- No motion duration or easing other than `ref.motion`'s six durations and one easing; no CSS transition invented per component.
- No image width outside the closed ladder (320/480/768/1024/1440/1920), no `sizes` outside the `Image` component's slot contract, no original-file thumbnails.
- No z-index numbers — `comp.shell.z-*` only.
- No PWA artefacts: no manifest link, no service-worker registration, no theme-color meta beyond the page ground — the `pwa.theme-color` token is **not** consumed by this surface.
- The `noindex` header/meta is a Worker concern (Hue's build brief), but the design records it here so it is not lost: it applies to museum HTML only, never to media responses (GOAL.md).
